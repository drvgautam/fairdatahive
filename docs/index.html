FairDataHive

A FAIR-compliant research data catalog built on W3C DCAT 3, FastAPI, and PostgreSQL.

FastAPI 0.111 Python 3.12 PostgreSQL 16 + pgvector DCAT-AP 3 FAIR OAI-PMH React 18 + Vite

Overview

FairDataHive is a self-hosted research data management system that lets teams register, describe, version, publish, and share datasets following open standards. It replaces ad-hoc file shares and spreadsheet catalogs with a structured, searchable, and interoperable repository.

Catalog Management

Create and publish versioned dataset records with rich DCAT metadata.

Dual-mode Search

Keyword search (FTS + tag matching) and semantic vector search over published catalog resources.

FAIR Scoring

Automatic per-resource FAIR assessment with actionable improvement suggestions.

RDF Export

Machine-readable Turtle and JSON-LD exports per resource and catalog-wide.

OAI-PMH

Standards-based harvesting endpoint for external portal integration.

Access Control

Private resources with owner-managed access request workflows.

Architecture

FairDataHive follows a layered service architecture. The backend stack runs in Docker Compose; the React UI runs locally with Vite during development, or as static files served by the API after npm run build. There is no containerized Vite service — that pattern duplicated port 5173 and caused a second dev server on 5174.

Quick Start

Prerequisites

  • Docker ≥ 24 and Docker Compose v2
  • Ports 5173, 8002, 9002, 9003, 5434 available on the host (Redis is internal-only)

Start the full stack

  1. Clone the repository and enter the project directory. 
    bashgit clone <repo-url>
cd fairdatahive
  2. Create your environment file. 
    bashcp .env.example .env

    The defaults work out of the box for local development. See Configuration for a full reference.

  3. Build and start all services. 
    bashdocker compose build
docker compose up -d

    Starts postgres, minio, redis, and api only — not a Vite/Node UI container. The API runs Alembic migrations on startup; wait ~15 seconds on first boot.

  4. Verify the API is healthy. 
    bashcurl http://localhost:8002/api/v1/health
# {"status":"ok","components":{"database":"ok","cache":"ok"}}
  5. Start the React UI (separate terminal). 
    bashcd frontend
cp .env.example .env
npm install
npm run dev

    Open http://localhost:5173. Vite proxies /api, /swagger, and /openapi.json to :8002. Project documentation is served at /docs from the docs/ folder. Only one dev server should run on port 5173; npm run dev clears any orphan on 5174 automatically.

  6. Optional — production-like UI without Vite. 
    bashcd frontend && npm run build
docker compose build api && docker compose up -d --force-recreate api

    Open http://localhost:8002/ui/ (root / redirects there).

Deployment

FairDataHive is designed as a self-hosted data management service: metadata and search live in PostgreSQL, binaries in S3-compatible object storage, and the API orchestrates FAIR cataloguing, access control, and interoperability endpoints. This section describes how to deploy that stack reliably for lab, consortium, or institutional use — not only “start containers”, but the operational choices that keep catalogs findable, downloadable, and auditable over time.

Topology and components

Treat FairDataHive as a small platform, not a single process. Each component has a distinct failure domain and scaling profile:

ComponentRolePersistenceNotes
API (FastAPI)REST, RDF, OAI-PMH, presigned URLs, FAIR scoringStatelessCPU/RAM for embeddings on semantic search; rebuild image on release
PostgreSQL 16 + pgvectorCatalog metadata, FTS, vector index, auditDurable volumeBack up regularly; extensions required at init
MinIO / S3Uploaded files and ZIP extractsDurable volume or external bucketMust be reachable from API and browsers (see public endpoint)
RedisSearch result cacheOptional persistenceSafe to flush; cache rebuilds on traffic
Keycloak (optional)OIDC/JWT issuerIts own DB in real deploymentsCompose profile auth is dev-oriented only
React UIHuman catalog interfaceStatic files in frontend/distServed by API at /ui or separate CDN

The bundled docker-compose.yml maps host ports to avoid clashes on developer machines (8002 API, 5434 Postgres, 9002/9003 MinIO). In production behind a reverse proxy you typically expose 443 only and keep data services on an internal network.

Prerequisites

  • Container runtime — Docker 24+ and Compose v2 (or an equivalent orchestrator).
  • Host resources — minimum 4 GB RAM for a pilot (8 GB+ recommended once semantic search and concurrent uploads matter). Disk: Postgres + object storage grow with catalog size; plan object storage separately from DB.
  • Network — stable DNS for the public catalog URL; outbound HTTPS if using DataCite or external IdP.
  • Secrets store — production credentials must not live in git; use a vault, compose secrets, or orchestrator secrets.
  • TLS termination — HTTPS at the edge (reverse proxy or load balancer) for UI, API, and presigned download URLs.

Deployment models

Single-host Compose

Fastest path: one VM runs Postgres, MinIO, Redis, and API together. Ideal for pilots, lab deployments, and consortium sandboxes.

Compose + external managed services

Run only the API container (or API + Redis) and point DATABASE_URL and S3 settings at managed RDS/Cloud SQL and institutional S3.

Kubernetes / Nomad

Split stateful sets (Postgres operator, MinIO tenant) from a stateless API Deployment. Use Ingress for TLS and path routing to /api/v1, /ui, /docs.

Regardless of model, preserve the two-endpoint MinIO pattern: an internal endpoint for the API container and a public endpoint embedded in presigned links returned to browsers. Mixing these is the most common production defect.

Docker Compose (single host)

The reference stack is defined in docker-compose.yml. Migrations run automatically when the API container starts (RUN_MIGRATIONS=true in the entrypoint).

  1. Prepare configuration. 
    bashcd fairdatahive
cp .env.example .env
# Edit .env — see “Production environment” below
  2. Build the API image (after any code or dependency change): 
    bashdocker compose build api
  3. Start data services and wait for Postgres. 
    bashdocker compose up -d postgres minio redis
docker compose ps   # postgres should show “healthy”
  4. Start the API. 
    bashdocker compose up -d api
docker compose logs -f api   # watch migrations, then “Application startup complete”
  5. Verify health and catalog surface. 
    bashcurl -s http://localhost:8002/api/v1/health | jq .
curl -s http://localhost:8002/api/v1/oai?verb=Identify | head

    Open documentation and Swagger on the host port you publish.

⚠

Do not run a Dockerized Vite dev server in production. Use a static build served at /ui (see below). A second Node container caused duplicate ports and root-owned caches in development; it is intentionally removed from Compose.

Serving the React UI

The catalog UI is a static SPA. For production, build once and let the API serve it from frontend/dist (mounted when the directory exists at image build time or copied in). 

bashcd frontend
npm ci
npm run build
cd ..
docker compose build api
docker compose up -d --force-recreate api

Users open https://<your-host>/ui/ (the API redirects / when the build is present). Set CORS_ORIGINS to your public UI origin if the UI is hosted on another hostname; when served from the same API host, CORS is less critical but token-based API calls from browsers still require correct origins if split.

For CDN deployment, upload frontend/dist/* and point the CDN at the same VITE_API_BASE public API URL used at build time, or rebuild with VITE_API_BASE=https://catalog.example.org/api/v1.

Object storage

MinIO in Compose (default)

The API talks to MinIO on the internal Docker network (MINIO_ENDPOINT=http://minio:9000). Browsers must never receive that hostname in presigned URLs.

VariableCompose / devProduction example
MINIO_ENDPOINThttp://minio:9000Internal service URL (K8s DNS, VPC endpoint)
MINIO_PUBLIC_ENDPOINThttp://localhost:9002https://s3.catalog.example.org or public MinIO ingress
MINIO_BUCKETfairdatahive-catalogInstitutional bucket name; create before first upload

After changing MINIO_PUBLIC_ENDPOINT, recreate the API container. Test by publishing a resource, downloading a file, and confirming the presigned URL host matches what clients can resolve.

External S3 (AWS, Ceph, institutional MinIO cluster)

FairDataHive uses S3-compatible APIs via aioboto3. Point MINIO_ENDPOINT at the vendor endpoint, set keys and bucket, and set MINIO_PUBLIC_ENDPOINT to the same public base users hit (or CloudFront in front of the bucket). Ensure CORS on the bucket allows GET from your catalog origin if browsers fetch objects directly.

Database and migrations

PostgreSQL must include the vector extension (image pgvector/pgvector:pg16 in Compose). The API runs alembic upgrade head on startup when RUN_MIGRATIONS=true.

  • First deploy — start Postgres, then API once; confirm logs show migrations applied.
  • Upgrades — pull new image, run docker compose up -d --force-recreate api; entrypoint migrates before serving traffic.
  • Manual migration — docker compose run --rm --entrypoint alembic api upgrade head
  • Backup — snapshot the postgres-data volume or use pg_dump on a schedule; test restore on a staging instance before you need it.
  • Connection string — use postgresql+asyncpg:// form in DATABASE_URL; pool sizing is handled by SQLAlchemy defaults unless you tune at the proxy layer (PgBouncer recommended for large fleets).
ℹ

Metadata tombstones remain in Postgres when resources are deleted; files are removed from object storage. Backup policy should cover both DB and bucket for full recovery.

Authentication in production

Disable development authentication everywhere except local laptops: 

envDEV_AUTH_ENABLED=false
KEYCLOAK_URL=https://idp.example.org
KEYCLOAK_REALM=fairdatahive

The API validates JWTs via JWKS (python-jose, RS256, issuer checked). Configure your IdP (Keycloak or institutional OIDC) to issue tokens with a stable sub claim — that value becomes owner_sub / publisher_sub on records. The Compose auth profile (docker compose --profile auth up -d auth) runs Keycloak in start-dev mode; for production, run Keycloak (or another IdP) as its own hardened deployment with a dedicated database and TLS.

UI users paste or store access tokens in the catalog header, or you integrate your institution’s OAuth2 proxy in front of the UI and API. Plan token lifetime and refresh according to your security policy; FairDataHive does not implement refresh-token flows itself.

Operations: backup, upgrade, monitoring

Backup strategy

  • PostgreSQL — nightly logical dump or volume snapshot; retain 30+ days for catalog compliance.
  • Object storage — versioning/replication on the bucket; lifecycle rules for cost.
  • Configuration — version-control .env templates without secrets; store secrets in a vault.

Upgrades

  1. Snapshot DB and note current image tag.
  2. Build/pull new API image; run migrations on staging first.
  3. docker compose up -d --force-recreate api (or rolling update in K8s).
  4. Smoke-test: health, search, upload, download presign, OAI Identify.
  5. Rebuild UI if API paths or env changed: npm run build then recreate API.

Monitoring

The API exposes Prometheus metrics at /metrics (instrumentator). Scrape from your monitoring network only. Combine with:

  • GET /api/v1/health — database and Redis connectivity
  • Container logs — structured via application logging; watch migration and presign errors
  • Disk usage on Postgres and object storage volumes
  • Redis memory — eviction is acceptable for cache but indicates heavy search load

Semantic search loads the sentence-transformers model on first use; expect a CPU/RAM spike after cold start — plan readiness probes with generous start_period if you autoscale API pods.

UI Usage Guide

Header controls

The top bar contains navigation links, a scope selector, and an authentication token field.

  • Scope selector — switches between the public catalog (all published resources) and a named project scope. When a project ID is entered, browse, search, and create operations are scoped to that project.
  • Token field — paste a JWT access token here for Keycloak-authenticated requests. With DEV_AUTH_ENABLED=true, this field can be left empty or set to any value.

Search

The Search page supports three modes selectable from the dropdown next to the search box. Only published, non-private resources in the current scope are searchable. See Search engine for implementation detail.

  • Auto (default) — keyword search first; if fewer than 3 hits, semantic results are merged in.
  • Keyword — best for titles, themes, and keyword tags (including short tags like a or comma-separated a,b,c,d). Uses PostgreSQL full-text search plus a token fallback when FTS misses (e.g. single-letter English stop words).
  • Semantic — best for natural-language questions (e.g. “impedance data for aluminium alloys”). Matches by meaning via embeddings stored at publish time; requires PostgreSQL + pgvector.

Facet filters for theme, license, and format appear once a query is submitted.

Creating a resource

The Create page registers a new DCAT dataset in the current scope. You need at least one distribution to publish; metadata and files can be combined in a single save.

  1. Navigate to Create in the top navigation.
  2. Fill in the metadata form.
    • Title — display name in the catalog and search results.
    • Description (min 50 characters) — what the data is and how to use it.
    • Keywords (min 2, comma-separated) — discovery tags for search and facets.
    • Theme — research domain from the catalog vocabulary.
    • License — SPDX-style licence; required before publish.
    • Private resource — when checked, downloads require owner approval via access requests.

    Additional fields (provenance, spatial/temporal coverage, DOI, language) are available via the API when creating or patching a resource.

  3. Add at least one distribution. Each option adds a separate dcat:Distribution; you may use one or several.
    • File upload — data stored in FairDataHive (MinIO). Files upload as you select them; ZIP archives are unpacked and each member can be linked. Download on the resource page uses a presigned URL.
    • External URL — a link to data hosted elsewhere (Zenodo, Figshare, a lab file server, a landing page). Recorded as access_url only. Use for static files or human-oriented pages, not for describing a programmatic API.
    • API / data service URL — the root of a REST or other machine-facing service. Recorded as both access_url (where to reach the data) and a linked dcat:DataService with endpoint_url (for RDF export and harvesters). The Create form sets both to the same URL. Use when consumers call an API rather than download a fixed file.
    ↔

    External URL vs API — same hostname, different intent: external = “get the file or page here”; API = “access via a data service”. Example external: https://zenodo.org/…/files/data.csv. Example API: https://api.example.com/v1/measurements.

  4. Save as draft or publish immediately. Enabling Publish immediately runs the publish guard after saving (licence, at least one distribution, FAIR score ≥ threshold). If the guard fails, the record stays a draft and failing checks are shown on the resource page.

Resource detail page

The resource page shows:

  • Full metadata and version history (sidebar)
  • FAIR score breakdown with suggestions (sidebar)
  • Distributions with Download buttons (generates a presigned URL)
  • Actions: Publish (for drafts), Landing page link, RDF (Turtle) link
  • Access request button (for private resources the user cannot download)

Data Model

The catalog model follows W3C DCAT 3 concepts.

Resource

A logical dataset identified by a stable base_resource_id. Owns all versions. Has a scope and an owner (user sub).

ResourceVersion

One snapshot of metadata and files. States: draft → published → deprecated. Carries all DCAT fields.

Dataset

Logical grouping of distributions within a version. Maps to dcat:Dataset.

Distribution

A single access point — upload (MinIO), external link (access_url), or api service (access_url plus dcat:DataService). See Creating a resource for when to use each.

Version lifecycle

POST /resources  →  draft
                    │
                    ▼  (publish guard passes)

                                    │
                                    ▼  (owner creates new version)
                              POST /versions  →  new draft
                                    │
                                    ▼
                              POST /publish  →  new published  ←── current version
                              (previous version transitions to deprecated)

DELETE /resources  →  tombstone  (data_deleted=true, metadata retained)

Scopes

Every resource carries a scope string — either "public" or an arbitrary project identifier. Scopes are not enforced by membership; they function as a namespace and filter. Any authenticated user may create resources in any scope.

FAIR Scoring

Each resource version receives a FAIR score in the range [0.0, 1.0] computed as the average of four dimension scores. Each dimension score is the fraction of passing checks within that dimension.

F

Findable

  • Has a non-empty title
  • Description ≥ 50 characters
  • At least 2 keywords
  • Theme is set
  • DOI is registered
A

Accessible

  • At least one distribution
  • Access rights defined (for private resources)
  • Access or download URL present on all distributions
I

Interoperable

  • License is set
  • Language (BCP-47) is set
  • IANA media type on all distributions
  • Publisher profile is resolvable
R

Reusable

  • Provenance description present (≥ 20 chars)
  • Rights statement present
  • SHA-256 checksum on all uploaded files
ℹ

The overall FAIR score must meet or exceed FAIR_SCORE_PUBLISH_THRESHOLD (default 0.40) before a draft can be published. The API returns actionable suggestions for each failing check.

Authentication

FairDataHive uses Bearer JWT authentication. Tokens are validated against the JWKS endpoint of a configured Keycloak realm. Authorization is resource-centric — the JWT sub claim is used as the owner and permission anchor; no Keycloak roles are enforced by the application.

JWT validation flow

  1. Request arrives with Authorization: Bearer <token>.
  2. API fetches JWKS from Keycloak (cached for 1 hour).
  3. Token is verified with python-jose (RS256, issuer checked, audience not checked).
  4. Claims are mapped to CurrentUser(sub, email, name, preferred_username).
  5. The sub claim is stored as owner_sub / publisher_sub on created records.

Development mode

Setting DEV_AUTH_ENABLED=true bypasses all JWT processing. Every request — including those without any Authorization header — is treated as dev-user. Do not use this in production or any shared deployment.

⚠

The React UI does not include an OIDC login flow. For Keycloak-authenticated deployments, obtain a token externally (Keycloak login page, client credentials, etc.) and paste it into the token field in the header bar.

Search Engine

Catalog discovery uses two complementary strategies: keyword search (lexical, indexed text) and semantic search (vector similarity). The unified endpoint GET /api/v1/search selects or combines them according to mode.

Keyword search (PostgreSQL FTS + token fallback)

A GIN index over to_tsvector('english', …) covers title, description, theme, and keywords (migrations 0002_search_indexes, 0004_expand_fts_index). The API builds the same combined text for plainto_tsquery and ts_rank. A two-step query (IDs + scores first, then entity load) avoids ORM eager-load conflicts.

English FTS drops very short tokens and can miss comma-separated keyword lists. When FTS alone would fail, a token fallback also runs:

  • The query is split on commas, semicolons, and whitespace (e.g. a,b,c,d → four terms).
  • All tokens must match (same intent as plainto_tsquery AND behaviour).
  • Tokens longer than two characters: case-insensitive substring match on title, description, theme, and keywords.
  • Short tokens (one–two characters): match keyword array elements only (exact element, case-insensitive), so a finds a keyword a but not the letter “a” inside fairdata.

A hit qualifies if either FTS or the token fallback matches. Use mode=keyword when searching by explicit tags or abbreviations.

Semantic search (pgvector)

Semantic search finds resources whose meaning is close to the query, not necessarily the same words.

  1. Indexing (on publish) — After a resource passes the publish guard, a background task concatenates title, description, keywords (space-separated), and theme (newline-separated blocks), then encodes the text with the configured sentence-transformers model (EMBEDDING_MODEL, default multi-qa-mpnet-base-dot-v1). The 768-dimensional vector is stored in resource_version.embedding (pgvector). Embeddings are not refreshed on later metadata edits unless the resource is published again.
  2. Query — The user query is encoded with the same model (CPU-bound; first use downloads model weights to the Hugging Face cache and loads the model in-process).
  3. Retrieval — PostgreSQL ranks rows by cosine similarity (1 − (embedding <=> query_vector)), using an HNSW index (idx_rv_embedding). Only rows with a non-null embedding and similarity ≥ SEMANTIC_SEARCH_THRESHOLD (default 0.30) are returned, ordered by score descending.

Semantic search requires PostgreSQL with pgvector; it is disabled on SQLite (unit tests). Private published resources are excluded from catalog search the same as for keyword mode.

Auto mode

Keyword search runs first. If the result count is fewer than 3, semantic search is also run. Unique semantic results are appended to the keyword list (no duplicate version IDs). The response uses "mode_used": "auto". Vague natural-language queries with few lexical hits benefit most; precise keyword or tag queries should use mode=keyword.

Caching

Results are cached in Redis keyed by a SHA-256 hash of the query parameters. TTLs are 300 seconds for keyword results and 120 seconds for semantic results. The cache for a scope is invalidated whenever a resource in that scope is published or deleted. After deploying search changes, restart the API and expect cached responses to expire within the TTL (or flush Redis in development).

You need a running PostgreSQL 16 instance with the pgvector extension enabled, plus Redis and MinIO (or a local MinIO binary).
